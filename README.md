# LoopCam

A rolling-buffer dashcam. Press **Play** once and forget about it: the app holds
only the most recent window of footage, never the whole trip. **Save** commits
that window to permanent storage without interrupting recording. **Stop** throws
the whole buffer away.

Full spec: [`docs/LoopCam_Development_Plan.pdf`](docs/LoopCam_Development_Plan.pdf).
Section references throughout the code (`§2.3`, `§7.1`, …) point at it.

## Stack

| Layer | Choice |
| --- | --- |
| Shell | React Native 0.86 via Expo SDK 57 (new architecture), TypeScript |
| Native bridge | Local Expo Module — `modules/loopcam-recorder` |
| Android capture | CameraX (`camera-video`), foreground service of type `camera` |
| iOS capture | AVCaptureSession + AVAssetWriter, screen-on driving mode |
| Merge on Save | MediaMuxer (Android) / AVMutableComposition passthrough (iOS) |
| Native projects | Generated by `expo prebuild` — `android/` and `ios/` are not committed |

The recording loop lives entirely in native code (§3.1): the JS thread can be
paused or blocked, and a dropped frame at a clip boundary means lost footage.
JS issues Play/Stop/Save and renders state; it is never in the recording path.

## Layout

```
App.tsx                        entry → RecorderScreen
src/
  hooks/useRecorder.ts         mirrors native state into the UI
  screens/RecorderScreen.tsx   driving screen: preview, buffer meter, 3 buttons
modules/loopcam-recorder/
  src/                         typed JS API, shared types, §2.2 preset math
  android/…/
    SegmentController.kt       §2.3 state machine + §2.4 ring buffer
    RingBuffer.kt              fixed-capacity deque; eviction = delete oldest
    CameraXSegmentRecorder.kt  one Recorder per session, one recording per clip
    RecordingService.kt        §5.1 foreground service (background survival)
    StorageManager.kt          §7.1 paths, naming, orphan cleanup
    ClipMerger.kt              §4 stream-copy concat on Save
  ios/                         same decomposition in Swift
    LiveActivityBridge.swift   recorder half of the iOS Lock Screen card
targets/widget/                iOS Live Activity, linked by @bacons/apple-targets
  Shared/                      also compiled into the app target (see plugin)
plugins/withLoopCamLiveActivity.js
```

Android and iOS deliberately mirror each other file-for-file, so a change to the
buffer rules has one obvious counterpart on the other platform.

## Running

```bash
npm install
npx expo prebuild            # regenerate android/ and ios/
npx expo run:android         # device recommended — the emulator's camera is fake
npx expo run:ios
```

`npx expo start` alone is not enough: the recorder is a native module, so it
needs a dev build, not Expo Go.

## Signing

**`LoopCam.keystore` is committed to this public repo.** That is a deliberate
choice, and it means the key must be treated as public: anyone can download it.
The passwords are the only thing standing between a cloner and the ability to
sign an APK that Android accepts as a genuine update to `com.damjano.dashcam`,
so they are *not* in the repo and must never be added to it.

`android/` is regenerated by prebuild, so signing is re-injected on every run by
[`plugins/withAndroidSigning.js`](plugins/withAndroidSigning.js). To build a
release on a fresh clone, supply three values as environment variables or as
Gradle properties in `~/.gradle/gradle.properties` (outside the repo):

```bash
export LOOPCAM_KEYSTORE_PASSWORD=…   # store password
export LOOPCAM_KEY_ALIAS=…           # alias of the key inside the store
export LOOPCAM_KEY_PASSWORD=…        # key password; defaults to the store password

npx expo prebuild -p android
cd android && ./gradlew bundleRelease   # → app/build/outputs/bundle/release/*.aab
```

Debug builds need none of these — Gradle resolves them lazily, so only a release
build fails if they are unset, and it fails at signing rather than quietly
producing a debug-signed artifact.

**iOS signing is not in this repo and cannot be.** Certificates and provisioning
profiles are issued to an Apple Developer account and live in your Keychain; a
fresh clone gets none of them. Building to a device needs that account, plus
`ios.appleTeamId` in `app.json` — prebuild warns about the missing value today,
and the Live Activity extension will not sign without it.

### One upstream patch

`patches/expo-modules-jsi+57.0.4.patch` works around an upstream build failure:
`abs()` in `JavaScriptCodable+Date.swift` is ambiguous under Swift 6.2 / Xcode 26
once the C++ `jsi` module is in scope, so iOS won't compile without it. It is
applied automatically by the `postinstall` hook (`patch-package`). Drop the patch
once Expo ships a fix.

## Status

Scaffolding for Phase 0/1. What is real: the state machine, the ring buffer and
its eviction, storage layout and orphan cleanup, the JS↔native contract, and the
UI. What is stubbed, each marked `TODO(phase-N)` at the exact call site:

- `CameraXSegmentRecorder.prepare` — binding the session on the main thread.
- `AVSegmentRecorder` — the whole AVAssetWriter segment loop.
- `ClipMerger.concatenate` (both platforms) — Save currently throws rather than
  silently reporting a successful save.
- Location sidecar (§7.1), impact detection (§8), storage budget enforcement (§7.2).

## Two things worth knowing up front

**iOS cannot promise background recording** (§5.2). Android's foreground service
is a real OS contract; iOS has no equivalent for camera capture. The plan's
recommendation, which the code follows, is a screen-on "driving mode" on iOS
(`isIdleTimerDisabled`) and to set that expectation during onboarding.

**Background controls are per-platform.** Android's foreground-service
notification carries Save and Stop. iOS gets a Lock Screen **Live Activity**
(`targets/widget`) with the same two buttons — `LiveActivityIntent`, so a tap is
performed in the app's process and reaches the same engine calls the in-app
buttons use. It does not make iOS record in the background; it is the control
surface and status readout for a session you can no longer see. Set
`ios.appleTeamId` in `app.json` before building to a device, or the extension
will not sign.

**Save never pauses recording** (§2.3). It snapshots the closed clips, hands
them to a background merge queue, and starts a fresh window immediately. The
in-progress clip is excluded on purpose — merging a file that is still being
written is the corruption risk called out in §10 — and it becomes the first clip
of the next window.
